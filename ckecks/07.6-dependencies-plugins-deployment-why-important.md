# 7.6 — Dependency downloads vs plugin downloads vs deployment: why the distinction matters

## Why 7.6 is important
**One Maven execution can use different repository collections, repository IDs, URLs, credentials, and permissions.** A correct token/server mapping for ordinary dependencies does not automatically make plugin retrieval or artifact deployment work.

For your current `mvn clean install` **401**, plugins are especially relevant: Maven typically needs plugins for the `clean`, compile, test, jar, and install lifecycles. A build can fail while fetching a plugin or its dependencies **before reaching your application's dependencies**. `mvn clean install` does **not** deploy your artifact to Nexus; that is generally `mvn deploy`.

## 1. Compare the three paths

| Operation | Repository declarations | Typical URL/ID after mapping | Credentials chosen from | Trigger |
|---|---|---|---|---|
| Project dependency download | `<repositories>` plus parent/super POM/profiles | E.g. mirror `company-nexus` | `<server id="company-nexus">` | Build resolving JARs/POMs |
| Maven build plugin download | `<pluginRepositories>` plus parent/super POM/profiles | E.g. mirror `company-nexus` | `<server id="company-nexus">` | `mvn clean install` lifecycle |
| Artifact deployment/upload | `<distributionManagement>` or an explicitly supplied alternate deployment repository | E.g. hosted repo ID `nexus-releases` | `<server id="nexus-releases">` | `mvn deploy` |

**Subtlety:** even if dependencies and plugins use separate source repository lists, a `mirrorOf=*` configuration can redirect both to the **same** corporate Nexus group URL and therefore the same selected mirror ID.

## 2. Example: download configuration

```xml
<!-- ~/.m2/settings.xml -->
<settings>
  <mirrors>
    <mirror>
      <id>company-nexus</id>
      <mirrorOf>*</mirrorOf>
      <url>https://nexus.company.com/repository/maven-public/</url>
    </mirror>
  </mirrors>
  <servers>
    <server>
      <id>company-nexus</id>
      <username>TOKEN_USERNAME</username>
      <password>TOKEN_PASSWORD</password>
    </server>
  </servers>
</settings>
```

With this mirror, dependencies and plugins can both resolve through `company-nexus`, subject to effective repositories and mirror matching.

## 3. Example: deployment configuration

```xml
<!-- pom.xml -->
<distributionManagement>
  <repository>
    <id>nexus-releases</id>
    <url>https://nexus.company.com/repository/maven-releases/</url>
  </repository>
  <snapshotRepository>
    <id>nexus-snapshots</id>
    <url>https://nexus.company.com/repository/maven-snapshots/</url>
  </snapshotRepository>
</distributionManagement>
```

Then put matching server IDs in `settings.xml`:

```xml
<servers>
  <server>
    <id>nexus-releases</id>
    <username>TOKEN_USERNAME</username>
    <password>TOKEN_PASSWORD</password>
  </server>
  <server>
    <id>nexus-snapshots</id>
    <username>TOKEN_USERNAME</username>
    <password>TOKEN_PASSWORD</password>
  </server>
</servers>
```

The Nexus admin must also grant the account **write privileges** to those hosted repositories; download permission alone does not imply upload permission. A Nexus **group repository** is usually intended for aggregate reads; uploads generally target a **hosted** repository.

## 4. The confusing failure scenario

```text
mvn clean install
  ├─ clean plugin resolution      ← 401 here? build stops
  ├─ compiler plugin resolution
  ├─ dependencies
  ├─ tests
  └─ local install into ~/.m2/repository

mvn deploy
  ├─ build / test lifecycle
  └─ upload to configured distributionManagement repository
```

Thus: 'My `settings.xml` has a correct `<server id="nexus-releases">`' does **not** prove the build can download the `maven-clean-plugin` from a mirror named `company-nexus`.

## 5. Identify the failing operation

```bash
mvn -X -e clean install > /tmp/maven-operations.log 2>&1

grep -Ein 'Downloading from|Using mirror|plugin|Could not transfer|401|Unauthorized' \
  /tmp/maven-operations.log
```

Interpret artifact coordinates:

| Example failing artifact | Likely kind | Config to inspect |
|---|---|---|
| `org.apache.maven.plugins:maven-clean-plugin` | Build plugin | Plugin repositories → mirror → server ID |
| `org.springframework:spring-core` | Project dependency | Repositories → mirror → server ID |
| Your company's artifact with `mvn deploy` | Upload target | `distributionManagement` ID → server ID and write privileges |

Maven's debug output may include plugin dependencies and metadata lookups. Confirm the exact failed URL before classifying.

## 6. Common mistakes

| Mistake | Consequence | Correction |
|---|---|---|
| Credentials for `nexus-releases` only | 401 on `company-nexus` downloads | Add correct mirror server ID |
| Assuming `<repositories>` covers plugins | Plugin resolution may use distinct sources | Inspect `<pluginRepositories>` and effective POM |
| `mirrorOf=*` interpreted as upload routing | Unexpected deployment behavior | `distributionManagement` controls deploy destination |
| Nexus UI SSO login used as Maven credentials | 401 with generated-token auth required | Use issued Nexus token pair |
| Read access mistaken for deployment rights | Upload 401/403/policy rejection | Verify write privileges and repository target |

## 7. Acceptance criterion
For the failing transfer, record **kind** (dependency/plugin/deploy), **repository ID**, **exact endpoint URL**, and **matching server ID**. For deploy, additionally verify write permission and version/release policy. Only then test with a comparable curl request.
