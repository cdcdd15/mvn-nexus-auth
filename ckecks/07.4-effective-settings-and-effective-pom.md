# 7.4 — Inspect effective settings and effective POM

## Goal
Determine the **actual configuration Maven uses** after combining user/global settings, active profiles, parent POMs, and Maven defaults. In a corporate environment, an IDE or wrapper may use settings different from the files you manually edited.

| Artifact | Shows | Does not reliably prove |
|---|---|---|
| Effective settings | Mirrors, servers (passwords normally masked), proxies, active settings profiles | That a specific HTTP Authorization header was sent |
| Effective POM | Inherited repositories, plugin repositories, effective dependency/build structure | Final mirror-to-server credentials by itself |
| `mvn -X` | What URL / repository ID was actually selected during a failing build | Safely readable credentials |

## 1. Confirm Maven and JVM

```bash
mvn -version
```

Record Maven version, Java version and Java home. The commands below should use the **same `mvn` executable and invocation context** as the failing build.

## 2. Generate effective settings

```bash
mvn help:effective-settings -Doutput=/tmp/maven-effective-settings.xml
```

**Warning:** Maven may need to resolve the Help Plugin through Nexus before writing this file. A 401 here does not invalidate the troubleshooting method: use `mvn -X` plus a manual review of settings as fallback.

Inspect the file **locally**, not in public ticket comments. Sensitive parts are typically masked by the Help Plugin, but do not assume every configuration field is safe to share.

Look for:

```xml
<mirrors>
  <mirror>
    <id>company-nexus</id>
    <mirrorOf>*</mirrorOf>
    <url>https://nexus.company.com/repository/maven-public/</url>
  </mirror>
</mirrors>
<servers>
  <server>
    <id>company-nexus</id>
    <username>TOKEN_USERNAME</username>
    <password>***</password>
  </server>
</servers>
```

`***` is an **illustrative masking marker**, not a token value to put in your settings.

## 3. Generate effective POM

```bash
mvn help:effective-pom -Doutput=/tmp/maven-effective-pom.xml
```

Inspect both `<repositories>` and `<pluginRepositories>`. Maven may inherit repository definitions from a parent POM or activate additional repositories through profiles. The super POM normally provides Maven Central. `effective-pom` is not the final URL after mirror selection; use 7.3 to prove the selected mirror.

## 4. Track each configuration layer

| Source | Typical location | What to check |
|---|---|---|
| User settings | `~/.m2/settings.xml` | mirrors, servers, profiles, proxies |
| Global settings | Maven installation `conf/settings.xml` | company defaults, mirrors/proxies |
| Alternate user settings | `mvn -s /path/settings.xml ...` | CLI overrides |
| Alternate global settings | `mvn -gs /path/settings.xml ...` | CLI overrides |
| Project POM | `pom.xml` | repositories, pluginRepositories, parents |
| Maven project JVM flags | `.mvn/jvm.config` | affects JVM, not repository declarations directly |
| Maven CLI defaults | `.mvn/maven.config` | may add `-s` / other Maven args |
| Environment / CI / IDE | tool configuration | can select a different Maven installation or settings file |

For a controlled comparison, use an **explicit settings file**:

```bash
mvn -s "$HOME/.m2/settings.xml" -X clean install
```

This chooses the user settings file explicitly. It does not override every other source (for example, global settings and project configuration still participate). Use `-gs` as needed to control global settings.

## 5. Why this matters for HTTP 401
Consider:

```text
POM:                  repository id=central
Effective settings:   mirror id=company-nexus, mirrorOf=*
Effective settings:   server id=nexus-release
Runtime download:     Downloading from company-nexus: ... → 401
```

The error is likely an **ID mismatch**. `nexus-release` credentials do not match the selected mirror ID `company-nexus`, even if the URL points to the same server.

Alternatively, an activated profile might point plugins to another repository not covered by your intended mirror. Examining both effective documents separates **source repository declarations** from **actual mirror selection**.

## 6. If Help Plugin itself fails
1. Run `mvn -X -e clean install` and capture mirror and URL lines.
2. Review user/global settings and `.mvn/maven.config` manually.
3. Confirm alternate `-s`/`-gs` values from shell, IDE, or pipeline.
4. If approved, run a known cached Help Plugin version in offline mode; otherwise avoid relying on this diagnostic command.
5. Do not replace a corporate configuration wholesale just to make `help:effective-settings` succeed.

## 7. Acceptance criterion
You can explain: (i) which Maven settings are loaded, (ii) which profiles/repositories exist, (iii) which mirror matches them, and (iv) which server ID supplies credentials. Treat this as a reproducible **configuration map**, not authentication proof until an artifact request succeeds.
